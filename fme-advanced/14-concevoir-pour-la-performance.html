Concevoir vite

Filtrer tôt, alléger, séparer dev et production

1Les définitions

Méthodologie de performance
Configurer un workspace pour qu'il tourne efficacement et fasse gagner du temps.
Error trapping
Concevoir le workspace pour que des données inattendues ne le fassent pas échouer.
Feature flag
Un paramètre utilisateur qui détourne les données pour activer ou non une partie du workspace.

2Filtrer et alléger

Filtrer en entrée

Filtrer les données en les lisant. Tout lire puis jeter coûte en performance. Le paramètre WHERE clause existe pour beaucoup de formats. Le FeatureReader ou le DatabaseQuerier restreignent aussi les données à la lecture.

Les feature types en trop

À l'ajout d'un reader, ne garder que les feature types utiles (et un canevas propre). Paramètres, Features to Read, Feature Types to Read : on peut le lier à un paramètre utilisateur avec une liste de choix.

Les attributs et listes

Les attributs absents du schéma de sortie ne servent à rien. Évite Merge attributes ou Generate list quand ce n'est pas nécessaire, et pour une liste, choisis le minimum d'attributs.

3Piéger les erreurs

Les outils

Filter, Tester : test simple ou plus complexe (a une valeur)
Logger : messages d'information, d'avertissement et d'erreur dans le log
Terminator : message d'erreur personnalisé
PythonCaller : port <Rejected> (reject_feature(), FeatureProcessor)

Plus complexe : un framework de validation et de test d'attributs (FME test framework, rTest).

4Authoring contre production

Deux étapes

On crée et on débogue un workspace dans FME Workbench, souvent en l'exécutant sur place. La version de production est différente : ce qui aide à créer et déboguer ralentit la traduction.

Logger et Inspector

Le Logger écrit dans le log, l'Inspector envoie les données au Data Inspector. À éviter en production : inutiles et coûteux, surtout le Data Inspector. Sur FME Flow, l'Inspector est ignoré. On les retrouve en filtrant dans Build, Transformers, Remove Transformers.

Le data caching

Gros impact sur la performance, inutile en production. Il n'affecte pas un workspace sur FME Flow. Activé ou désactivé via le menu du workbench (pas stocké dans le fichier).

Les parties désactivées

Une partie désactivée ou isolée pour tester diffère de la production : il vaut mieux la ranger dans un workspace séparé ou une version séparée. Pas d'impact réel sur le flux, il suffit de la regrouper. Pour une partie inutile, un paramètre utilisateur détourne les données (feature flag).

5Exercice : la marchabilité

Le sujet

Calculer la « walkability » de chaque adresse de Vancouver : la facilité d'accès aux services à pied.

Les étapes

Enregistrer en template avec les data caches pour voir la taille du cache
AttributeKeeper pour retirer les attributs et listes inutiles
Décocher les listes générées par l'Aggregator
Supprimer le feature type lu mais jamais utilisé
Réduire un bookmark pour éviter le cache en trop

Un transformer dont on n'a pas besoin d'inspecter la sortie est caché dans un bookmark réduit. File, Save as Template, cocher include data caches.

Le piège

Garde un Logger ou un Inspector en production et tu paies deux fois : temps d'exécution, et rien d'utile en retour.

À retenir

  • Filtre le plus tôt possible, dès la lecture.
  • Retire feature types, attributs et listes dont la sortie n'a pas besoin.
  • Piège les erreurs avec Tester, Logger, Terminator ou le port <Rejected>.
  • En production, retire Logger et Inspector et coupe le data caching.
  • Un bookmark réduit évite du cache inutile.

Un workspace rapide, c'est d'abord un workspace qui lit peu.
